从 C++ 到汇编：亲手观察函数调用

前四篇讲的是「机制」，这一篇动手验证。g++ -S（让编译器输出汇编——也就是 CPU 真正执行的底层指令的文本形式）和 objdump（把已经编好的机器码反向翻译回汇编的工具）就是我们的显微镜：把同一个 add 分别在 -O0（不优化，代码怎么写就怎么翻译）和 -O2（打开常规优化）下编译，亲眼看到优化后栈帧如何缩水、局部变量如何进寄存器、函数如何被内联、call 如何彻底消失——把前面所有抽象概念一次「落地」。

01

动手准备：g++ -S 与 objdump

两种把 C++ 变成汇编的方式，各有用处

先把下面这段代码存为 demo.cpp。它故意写得极简——只有一个 add 函数和一次调用，这样等它变成汇编后，每一条指令我们都能和源码对得上号：

int add(int a, int b) {
    int c = a + b;
    return c;
}

int main() {
    int result = add(10, 20);
    return result;
}
方式命令看到的是
编译期汇编g++ -S -O0 demo.cpp -o demo.s编译器生成的 .s 文本，带标签/注释，最易读
反汇编目标文件g++ -c demo.cpp && objdump -d demo.o已汇编成机器码后再反汇编，接近最终二进制
更易读的语法g++ -S -masm=intel ...Intel 语法（本文采用，目的操作数在前）
在线工具Compiler Explorer (godbolt.org)源码与汇编并排高亮，改选项实时更新

本文的汇编一律用 Intel 语法（一种写法：mov dst, src，目的地写在前面）。GCC 默认输出的则是 AT&T 语法（另一种写法：mov src, dst，顺序正好反过来，寄存器名前面还带一个 % 号）。两种语法描述的指令完全相同，只是记法不同——就像同一段旋律的两种记谱法。编译时加 -masm=intel 这个开关，就能切到 Intel 风格。另外，不同编译器、不同版本给出的具体输出会有差异，这属于正常现象，不必纠结。

02

-O0 下的 add：教科书式栈帧

未优化，忠实还原前几篇讲的一切

# g++ -S -O0 -masm=intel demo.cpp
add(int, int):
    push    rbp                # 序言：保存旧帧基址
    mov     rbp, rsp           # 建立本帧锚点
    mov     DWORD PTR [rbp-20], edi   # 参数 a（EDI）落栈
    mov     DWORD PTR [rbp-24], esi   # 参数 b（ESI）落栈
    mov     edx, DWORD PTR [rbp-20]
    mov     eax, DWORD PTR [rbp-24]
    add     eax, edx           # a + b
    mov     DWORD PTR [rbp-4], eax    # c = a + b（局部变量在 [rbp-4]）
    mov     eax, DWORD PTR [rbp-4]    # 返回值放 EAX
    pop     rbp                # 结语：恢复旧帧基址
    ret

对照前面各篇讲的内容，全部要素都在这份汇编里了：序言/结语（函数开头和结尾那几条固定套路指令——开头保存旧的帧基址、搭好新栈帧，结尾再原样恢复，02 篇详细讲过）、参数走 EDI/ESI（两个参数分别装在这两个寄存器——CPU 内部取用速度极快的小储物格——里传进来，04 篇）、返回值走 EAX（约定俗成的「返回值专用格子」，调用方到这里来取结果）、局部变量 c 在 [rbp-4]（rbp 指向当前栈帧的基准点，从它往低地址偏移 4 字节就是 c 的位置）。-O0 就像慢动作回放，把每一步机制一帧不落地演出来。

03

-O2 下的 add：栈帧几乎消失

同一份代码，优化后判若两人

# g++ -S -O2 -masm=intel demo.cpp
add(int, int):
    lea     eax, [rdi + rsi]   # 一条指令算完 a+b 放 EAX
    ret                        # 直接返回

发生了什么？在 -O2 优化下，编译器看穿了这个函数的本质，于是把一切多余的动作都删掉了：

  • 局部变量 c 消失了 —— 它只是 a+b 的中转站，算完就没用了，没必要为它在内存或寄存器里留位置；
  • 没有 push rbp / sub rsp —— add 是叶子函数（不再调用任何其他函数的函数），既然没有下家要交代、也没有局部变量要安置，就不必搭栈帧（函数在栈上占用的那块工作空间）；
  • 参数没落栈 —— 两个参数从头到尾待在 RDI/RSI 这两个寄存器里，直接用 lea 一条指令相加完事。

这正是 02 篇与 01 篇反复强调的：「局部变量不一定在栈上」「函数调用不一定有栈帧」—— 这里就是活生生的证据。

lea 为什么能做加法？

lea（Load Effective Address，加载有效地址）本来是拿来算内存地址的，但「基址 + 偏移」这套地址计算本身就是一次加法。编译器借它一条指令完成加法，而且不改动标志位（标志位是 CPU 里记录上一次运算结果状态的一组小开关，比如「结果是否为零」），插在任何地方都不会干扰别人，这是常见的优化技巧。

04

逐条读懂关键指令

看汇编时最常遇到的这几条，记住即可

指令含义与函数调用的关系
mov dst, src数据搬运装载参数、存取局部变量
lea dst, [..]算地址（也用来做加法）取变量地址、快速算术
push / pop压栈 / 弹栈（RSP ∓ 8）保存/恢复寄存器、建帧
sub rsp, N / add rsp, N开辟 / 释放栈空间为局部变量分配、回收
call f压返回地址 + 跳转进入被调函数（03 篇）
ret弹返回地址 + 跳回返回调用者（03 篇）
leave= mov rsp,rbp; pop rbp拆栈帧（结语）

再看 main 里的调用点（-O0 版本），04 篇讲的传参和 call（调用指令：把「回来该执行哪条指令」这个返回地址压到栈上，然后跳进被调函数）在这里能一条条对上：

main:
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16
    mov     esi, 20            # 第二个参数 b = 20 → ESI
    mov     edi, 10            # 第一个参数 a = 10 → EDI
    call    add(int, int)      # 调用（压返回地址、跳转）
    mov     DWORD PTR [rbp-4], eax   # result = 返回值(EAX)
    ...
05

-O0 vs -O2 逐行对照

同一段 C++，两种世界

-O0（11 条指令）

push rbp
mov  rbp, rsp
mov  [rbp-20], edi
mov  [rbp-24], esi
mov  edx, [rbp-20]
mov  eax, [rbp-24]
add  eax, edx
mov  [rbp-4], eax
mov  eax, [rbp-4]
pop  rbp
ret

-O2（2 条指令）

lea eax, [rdi + rsi]
ret
方面-O0-O2
栈帧建立完整栈帧无栈帧（叶子函数）
局部变量 c在 [rbp-4]被优化掉
参数先落栈再取全程在寄存器
指令数112
可调试性好（每个变量可见）差（变量常在寄存器/被消除）

这解释了为什么 Release（-O2）版调试时 GDB 常显示 <optimized out>（GDB 是最常用的命令行调试器，能逐行执行程序、随时查看变量；这句提示的意思是「该变量已被优化掉，取不到了」）——因为变量根本不在内存里，它可能一直待在某个寄存器中，甚至从头到尾就不存在。所以生产环境排障常用 -O2 -g 折中：-g 的意思是「保留调试信息」，即优化照常开，但额外给调试器留一份变量与源码行号的对照表。

06

inline 与自动内联：call 直接消失

优化后连「函数调用」这件事本身都可能不存在

把 main 和 add 放在同一个文件里用 -O2 编译，add(10,20) 这行调用会被编译器内联并常量折叠（内联＝把函数体直接复制进调用处、不再真的发起调用；常量折叠＝参数都是已知常量时，编译器干脆在编译阶段就把结果算好）：

# g++ -S -O2 -masm=intel demo.cpp （main 部分）
main:
    mov     eax, 30            # add(10,20) 被内联并直接算成 30！
    ret                        # 没有 call add，没有传参

编译器的推理过程是这样的：它发现 add(10,20) 的两个参数都是编译期就已知的常量，函数体又极短，于是分两步走：① 先把 add 的代码复制嵌入 main 内部（inline），这样 call/ret 和传参的开销就全省了；② 再进一步，直接在编译阶段算出 10+20=30（常量折叠），连运行时加法都免了。最终二进制里既没有 add 这个函数、也没有任何对它的调用。

概念说明
inline 关键字主要是链接语义（允许多个 TU 有定义），是否真内联由编译器决定
自动内联即使不写 inline，-O2 也会内联它认为划算的小函数
不内联的情况函数太大、递归、取了函数地址、跨 TU 且无 LTO、显式 __attribute__((noinline))

如果想强制看到真实的 call，可以给 add 加上 __attribute__((noinline)) 标注（明确告诉编译器「这个函数不许内联」），或者把两个函数拆到不同文件分开编译（并且不开 LTO——LTO 是链接期优化，能让优化跨越文件边界继续进行）。这也提醒我们一个容易被忽略的事实：「运行时发生几次函数调用」是编译器优化后的产物，源码里写了几次调用，不代表运行时就真的调用几次。

07

别把某份汇编当成绝对规则

影响输出的因素太多

最后要泼一盆冷水：同一段 C++ 生成的汇编并不是唯一的。下面这张表里任何一项变了，输出就会跟着变：

变量举例
编译器与版本GCC 11 vs GCC 13 vs Clang 17
优化级别-O0 / -O1 / -O2 / -O3 / -Os
目标架构 / ABIx86-64 System V vs Windows x64 vs ARM64
指令集扩展-march=native 会用 AVX 等新指令
其它开关-fomit-frame-pointer、-flto、-fno-inline

所以正确的态度是：把任何一份汇编都当作「特定条件下的一个观测结果」，用它去验证机制是否如书中所说，而不是把它背下来当标准答案。掌握「怎么生成、怎么读」这套方法，比记住某条固定的指令序列重要得多。

08

核心结论

  • g++ -S 看编译器汇编，objdump -d 看反汇编，godbolt 最直观。
  • -O0 忠实呈现栈帧/传参/返回值；-O2 下栈帧可能消失、局部变量入寄存器或被删除。
  • inline 与自动内联能让 call 彻底消失，配合常量折叠函数可被算成一个常量。
  • 「源码里的函数调用」≠「运行时的函数调用」——后者是编译优化后的结果，可能被内联、折叠甚至整体消失。
  • 任何一份汇编都依赖编译器/优化/架构/ABI，只能作为验证机制的样本。
09

常见误区

❌ -O2 只是让代码执行得更快。 它会内联、删变量、消栈帧、常量折叠，从根本上改变代码结构与可调试性。

❌ 源码写了 call，二进制里就有 call。 内联后可能完全没有 call。

❌ inline 一定不会产生函数调用。 inline 只是建议 + 链接语义，是否内联由编译器定；反之不写 inline 也可能被内联。

❌ 某本书里的汇编就是标准答案。 换编译器/优化/架构，输出就变。

❌ 局部变量在汇编里一定看得到。 -O2 下常被优化进寄存器或消除，GDB 显示 <optimized out>。

10

面试问题

点击每道题展开参考答案（先自测，再对照）。

  1. 基础如何查看一段 C++ 对应的汇编？

    g++ -S 生成 .s；或 g++ -c 后 objdump -d 反汇编；或用 Compiler Explorer 在线并排查看。加 -masm=intel 用 Intel 语法。

  2. 原理为什么 -O2 后有时候看不到函数调用？

    编译器把小函数内联进调用点，省去 call/ret 和传参；若参数是常量还会常量折叠，最终二进制里没有该调用。

  3. 原理为什么 -O2 下 add 没有栈帧？

    它是叶子函数、局部变量可被消除，编译器判断无需栈帧，直接用寄存器计算并 ret。

  4. 汇编lea 为什么能做加法？

    lea 计算「基址+变址」地址表达式，本质就是加法，且不改标志位，编译器常借它做快速算术。

  5. 汇编inline 一定不会产生函数调用吗？

    不一定。inline 主要是链接语义与内联建议；能否内联由编译器决定，递归/过大/取地址等情况仍会真调用。

  6. 实战为什么 Release 版 GDB 里变量常显示 optimized out？

    优化把变量放进寄存器甚至完全消除，内存里没有对应位置，调试器无法取值。可用 -O2 -g 折中或降优化定位。

  7. 实战如何强制让编译器保留某次函数调用以便观察？

    给被调函数加 __attribute__((noinline))，或分文件编译且不开 LTO，或降到 -O0。
